Headline finding, before anything else: the single-parcel report page currently renders as a raw JSON dump inside a plain-text box — no formatted sections, no verdict, no visual hierarchy. Every buildability check underneath it is genuinely real and well-built. None of that shows up as a product yet. That gap, more than any missing feature, is what separates this from "world-class" today.

A · Current architecture

One Python module holds all business logic; a thin, deliberately stateless Flask layer serves it; the browser is the only place a customer's session data lives.

  • Backend — a single flat module (vacant_land_search.py, 2,914 lines) covering search, buildability, tax, zoning, skip tracing, and CSV/mail export. No package structure yet — everything is one file.
  • Web layer — Flask (webapp/app.py). Rebuilt 2026‑09‑12 to hold zero server-side session state: every parcel's raw data is sent to the browser at search time and handed back on every follow‑up call. Correct call for a multi‑subscriber product — see Finding E‑1.
  • Frontend — one HTML file, inline CSS/JS, no build step, no framework. Functional, not yet a product surface.
  • Hosting — Render free tier, single 0.5 CPU instance, no database, no queue, no CDN, spins down after 15 minutes idle.
  • Persistence — none server-side. Search results persist only in the browser's localStorage.
  • Deploy — GitHub → Render, direct to production. No staging environment, no automated test gate before a push goes live.

B · Current features (verified against the live code, not the feature list you handed in)

  • Vacant‑land search via Realie, hard two‑signal filter (use code and zero building area) to exclude anything with a structure
  • Acreage / county / city filtering
  • Current owner name, entity type, price paid, ownership duration
  • Owner mailing address, correctly separated from the parcel's own site address
  • Tax assessment values; tax/lien/foreclosure flags from Realie's own data
  • Tax delinquency lookup for 8 places with real government APIs — only 7 are wired into the website. New York City's lien‑sale check is fully built and tested in the backend but absent from the live UI (Finding R‑7).
  • Full buildability report: flood/wetland (parcel‑exact), septic suitability, 17‑hazard risk index, road access, coastal/habitat designations, nearby‑development proxy, slope, contamination, fine‑grained wildfire, broadband
  • Zoning district lookup for exactly two counties nationwide (unincorporated Miami‑Dade FL, unincorporated King County WA) — district name only, never setbacks or FAR
  • Map with severity‑colored markers and two heatmap overlays (land value, distressed concentration)
  • CSV export in mail‑merge order, owner mailing address prioritized over the property's own address
  • Skip tracing via the customer's own Tracerfy account, single and bulk, with a pre‑spend cost estimate
  • Print view; results persisted in the browser across refreshes
  • Dormant, unused: Regrid/ATTOM paid search path, a full PostGIS schema, a non‑functional contractor/permit stub

C · Current data sources

  • Realie.ai — parcel search, owner, valuation. Paid (25 free tokens/mo), bring‑your‑own‑key.
  • Tracerfy.com — skip tracing, ~$0.10/lookup typical, bring‑your‑own‑key, live‑confirmed working.
  • 8 government tax‑delinquency sources — King County WA, Pittsburgh PA, Philadelphia PA, Norfolk VA, Sonoma County CA, Richmond VA, Cache County UT, NYC. All real, official, free APIs — no nationwide source exists.
  • 9 free federal data sources — FEMA (flood + National Risk Index), USFWS (wetlands, critical habitat, coastal barriers), USDA (soil/septic), Census TIGERweb (roads), USGS (elevation), EPA (Superfund, Brownfields), USFS (wildfire), FCC (broadband), OpenStreetMap Overpass.
  • 2 free zoning sources — ArcGIS layers for Miami‑Dade and King County only.
  • Regrid / ATTOM — paid, integrated in code, never tested against a live account, not connected.

D · Strengths

  • Genuinely differentiated depth — a competitive audit run earlier found no single competitor combining verified vacancy, septic, contamination, road access, broadband, 17‑hazard risk, and real tax‑delinquency dollar amounts in one product.
  • A real track record of live‑testing catching production bugs before customers did — wrong auth header formats, a misattributed zoning source, a cumulative‑vs‑per‑year tax field, EPA field‑name casing.
  • Zero‑liability architecture for the two paid data sources — bring‑your‑own‑key avoids a resale model that both providers' own Terms of Service actually prohibit.
  • Correctness‑first backend design — the stateless rebuild specifically closes a cross‑customer data risk, not just a bug.
  • Honest limitation‑disclosure as a habit — most functions already document their own coarseness in code comments. The gap is that none of it reaches the customer‑facing screen (see Finding I‑1).

E · Weaknesses

  • E‑1 — Parcel detail is raw JSON in a <pre>‑style box. No formatted report, no verdict.
  • No accounts, auth, or billing anywhere — nothing can be sold yet.
  • Every buildability check runs against a synthetic ~110‑meter box centered on Realie's coordinate, not the parcel's real boundary — see Finding F‑1, the single biggest accuracy risk in the product.
  • No confidence or data‑completeness signal anywhere in the output.
  • No caching — the same parcel viewed twice re‑runs all ~12 external calls, and a repeat skip trace costs real money again.

F · Accuracy risks

Critical

F‑1 — Every polygon-based check runs on a fake parcel shape

Realie's search returns a center point, not a boundary. The report endpoint builds a placeholder ~110m box around that point and feeds it to flood/wetland scoring, road‑access, and environmental‑designation checks. The resulting buildability_score: 98.93 looks parcel‑precise. It is not — it's precise to a shape that isn't the parcel. This is disclosed in code comments; it reaches no customer‑facing text at all.

  • Hazard/NRI data is census‑tract level, already disclosed, but sits next to a %-score that reads as far more precise than it is.
  • Zoning returning nothing looks identical to zoning returning "confirmed clear" — there is no distinct "not covered here" state.
  • No cross‑validation against a second data source for any single fact — one county record, taken as given.

G · False‑positive risks

  • Flood/wetland percentage can be thrown off in either direction by the placeholder‑box mismatch, worst on odd‑shaped or coastal lots.
  • Fine‑grained wildfire tier cutoffs are the developer's own rough approximation, not an official USFS breakpoint.
  • A tax/lien flag can fire on data that's already been resolved if the county's own record is stale.

H · False‑negative risks

  • Road‑access relies on Census TIGER, which is known to omit legitimate private/rural roads — a real access point can silently read as landlocked.
  • Zoning silence (the common case, 2 counties covered nationwide) can be misread as "no zoning issue" rather than "not checked."
  • The nearby‑development utility proxy can read "likely served" from buildings on a different, unconnected utility grid.

I · UX problems

  • I‑1 — No synthesized verdict. The backend already computes a clean concerns[] list; the UI never elevates it into the "pursue / investigate / pass" answer a user actually wants (your own stated goal #7).
  • No visual severity difference between "landlocked" and "soil somewhat limited" — both currently render as identical plain‑text lines.
  • Fixed 380px sidebar, not responsive — a real problem for a mostly mobile‑first customer base.
  • A report that can take up to ~20 seconds shows only the word "Loading…"
  • The 8‑city tax‑delinquency tool sits disconnected from search results, requiring a customer to already know the target's ID format.

J · Performance

  • Fixed same day as this audit: a 110‑second report load, traced to 10 sequential external calls plus two unbounded retry loops, brought down to a consistent ~10–20 seconds via parallelization and a hard timeout. Still slow for a single click by modern SaaS standards.
  • Zero caching anywhere — identical requests cost identical latency and, for skip tracing, identical real money, every time.
  • Single free‑tier dyno cold‑starts after 15 minutes idle.

K · Security

  • No authentication on any endpoint — expected at this stage, but a hard blocker before billing.
  • Fixable in minutes renderResults() builds HTML via string interpolation of externally‑sourced fields (APN, acreage) without escaping — a low‑likelihood but real stored‑content injection path via third‑party data.
  • No rate limiting anywhere — both a cost‑abuse and infrastructure‑abuse surface once public.
  • Philadelphia's tax‑delinquency check already validates its input is numeric before building a raw SQL string — correctly defended, worth calling out as the pattern to replicate elsewhere, not a gap.

L · API‑cost risks

  • The Realie search key still supports a server‑side environment‑variable fallback. Today's deployment leaves it unset on purpose so every visitor pays their own way — but nothing in the code prevents a future operator from setting it and silently reverting to "the site owner pays for everyone."
  • No caching means a customer can pay Tracerfy twice for the same owner just by searching the same area again.
  • Free government APIs (Overpass, ArcGIS) were built for light individual use, not concurrent commercial load — no disclosed rate limit, real risk of the shared server IP getting throttled under real traffic.

M · Scalability

  • No database — no way to store accounts, saved leads, or search history yet.
  • Single dyno, no queue for slow external calls, no horizontal scaling path.
  • Realie's own free‑tier token model caps interactive search volume by design — fine for bring‑your‑own‑key, but rules out "scan an entire state" as a workflow without a paid tier.

N · Legal / liability

  • Buildability, septic, and zoning results could genuinely inform a real purchase decision. Every caveat about their limits lives in code comments a customer will never see — none of it reaches the live product's UI.
  • No Terms of Service or liability limitation live on the actual site (an anti‑scraping ToS draft exists but was never published or broadened into a general agreement).
  • No privacy policy for the PII the product handles — owner names, addresses, phone numbers — even though none of it is stored server‑side today.

O · Competitive weaknesses

  • No contact info bundled by default — competitors like PropStream and BatchLeads include skip tracing standard; this product requires a separate account.
  • No zoning/setback/FAR data beyond two counties — Buildability™ covers this nationally.
  • No visual polish and no mobile layout — every real competitor is a finished, professional product today.
  • No lightweight CRM/pipeline layer, which several competitors bundle.

P · Missing capabilities

  • No confidence/uncertainty scoring framework of any kind
  • No comps or similar‑recently‑sold signal
  • No saved searches or new‑match alerts
  • No multi‑area or multi‑state search in a single workflow
  • No accounts, billing, or tiered access

Q · Should be removed or simplified

  • The Regrid/ATTOM search path — untested against a live account, unused, real maintenance surface for zero current value
  • The full PostGIS schema and its three functions — entirely unused by the website
  • The contractor/permit market‑activity stub — already documented in its own code as non‑functional; either hide it or remove it rather than let it sit as dead weight
